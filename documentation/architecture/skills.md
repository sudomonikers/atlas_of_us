# How the Skills Module Works

This explains how the skills sub-graph gets filled out: where skills come from, what a user sees when they search for
one, how new skills get created and fleshed out, how the community keeps them honest, and how the rest of the Atlas
hears about it. For the graph itself, read `../data_model/skills/skills.md`.

## The problem
There are more skills in the world than we could ever write by hand, new ones appear all the time, and people describe
the same skill in many different ways. The skills graph is only useful if each skill exists **once**. If "Knife Skills"
and "Knife Handling" are separate nodes, two people with the same ability never meet in the graph, and everything built
on top of it (who you could become, job matching, recommendations) gets worse.

So the hard part of this module is not generating content, it's **identity**: deciding whether a skill is new, what it
is the same as, and where it sits relative to everything else. The design below is built around that.

## The approach in one paragraph
We start from an existing, curated skills taxonomy (ESCO) so the graph has a backbone on day one. Every skill starts as a cheap **stub**, and only gets its full Dreyfus content generated by an LLM when someone actually needs it. Anything a user types goes through **gates** before it can become a new node. Generated content is **provisional** until the community endorses it, and changes to it are **proposals** that only become the main version once the community accepts them. Every meaningful change is published as an **event**, so other modules (Topics, Physical Attributes, Jobs, and whatever comes next) can react without the Skills module knowing they exist.

## The pieces

| Piece | Where (planned) | What it does |
|---|---|---|
| UI | `application/ui/atlas-of-us-ui/src/skills/` | Search, the skill page, claiming a level, reviewing content and proposals |
| API | `application/apis/atlas-api/src/domains/skills/mod.rs` | Search, the creation gates, claiming levels, endorsements and proposals, publishing events |
| Gates and resolver | `application/apis/atlas-api/src/domains/skills/resolver.rs`, the resolver shared with the fill job | The gates normalize and classify what a user asks for, and screen out nonsense. The resolver decides whether a skill name is the same as, more specific than, or different from existing skills, and creates stubs |
| Fill job | `application/apis/atlas-jobs/src/skill_fill.rs` | Generates a stub's Dreyfus levels and prerequisites with Bedrock |
| Proposal job | `application/apis/atlas-jobs/src/skill_proposal.rs` | Screens a proposed change before it is opened to the community |
| Event bus | `application/infrastructure/events.tf` | The Atlas event bus, its archive, and one rule and queue per consumer |
| Taxonomy import | `application/database/skills_import/` | Loads ESCO skills, aliases and hierarchy as stubs |

### Models
- **The gates and the resolver's judge** use a fast model on Bedrock, set by `SMALL_MODEL` in `bedrock.rs` (Claude Haiku
  4.5). Each is one forced tool call whose input is the answer.
- **Embeddings** come from Amazon Titan Text Embeddings V2 on Bedrock, at 1024 dimensions. A skill's vector is an
  embedding of `"<name>. <description>. Also known as <alias>, <alias>."`, and a search is an embedding of what was
  typed. Why Titan is in `ADRs/skills_embeddings.md`.

### The API
All routes are under `/api/skills`. Asking, confirming and filling need a logged in user.

| Route | What it does |
|---|---|
| `GET /search?q=` | The closest skills, each with its broader skill |
| `POST /` `{query}` | Asks for a skill we don't have: runs the gates and the resolver, and returns an `outcome` of `not_a_skill` (with the `kind` it is), `rejected` (with a `reason`), `existing` (the skill it means, and an `alias_token` for the user's wording) or `created` (the new stub) |
| `POST /{id}/aliases` `{alias_token}` | The user confirmed "did you mean...?", so their wording becomes an alias |
| `GET /{id}` | A skill with its levels, its broader skill and its specializations |
| `POST /{id}/fill` | Asks for a `stub` or `failed` skill to be filled, and returns its status |

## Where skills come from
A Skill node is created in exactly three ways, and every one of them goes through the resolver so it can't create a
duplicate:

1. **The taxonomy import.** Our starting backbone.
2. **A user searching for something we don't have.** Goes through the gates first.
3. **The fill job naming a prerequisite we don't have.** Created as a stub, never filled until someone needs it.

### The taxonomy: ESCO
ESCO is the European Commission's classification of skills and occupations. It's free to use with attribution, and it
gives us what we would otherwise have to build ourselves:

- **About 14,000 skills,** each with a stable URI, a preferred name, a description and **alternative names** (in English
  and many other languages). The alternative names become aliases, which makes search and de-duplication work from the
  first day.
- **A hierarchy** of broader and narrower skills, which becomes our `SPECIALIZATION_OF` relationships.
- **Links between occupations and the skills they need,** which the Jobs module will want later.

How we import it:

- **Only the "skill/competence" entries become Skills.** ESCO also has "knowledge" entries (such as "French history").
  Those belong to the Topics sub-graph, and are left for it.
- **Each one is imported as a stub:** name, description, aliases, an embedding, its place in the hierarchy,
  and five empty Dreyfus levels. No LLM calls happen at import time.
- **Imports are re-runnable.** Nodes are matched on their name
- **ESCO is weak on hobbies and everyday skills** (surfing, juggling, sourdough). Those come in through users

## Skill identity

### What a Skill node carries
On top of what `../data_model/skills/skills.md` describes:

- `status`: where it is in its life (see below).
- `aliases`: every other name we know it by. When a user's search turns out to mean an existing skill, their wording
  is added here instead of becoming a new node.
- `vector`: an embedding of the name, description and aliases, used by the resolver.

### How skills relate to each other
There are three different relationships between skills, and keeping them apart matters:

- **Specialization:** `(Sourdough Baking)-[:SPECIALIZATION_OF]->(Baking)`. A narrower version of a broader skill. Comes
  mostly from ESCO, and from the resolver when a user names something more specific than what we have.
- **Prerequisite:** lives on the **levels**, not the skills, matching the data model. `(Cooking Competent)-[:REQUIRES
  {strength}]->(Knife Skills Advanced Beginner)`. Comes from the fill job.
- **Same skill:** one node, with the other name in its aliases.

### Statuses

| Status | Meaning |
|---|---|
| `stub` | Exists, can be found and linked to, but its levels are empty |
| `filling` | A fill has been requested and the job is working on it |
| `ready` | Its levels are filled and it can be claimed |
| `failed` | The fill job gave up. The user can retry, which puts it back to `filling` |

Every skill has its five Dreyfus level nodes **from the moment it's created**, even as a stub. That means anything can
link to a stub's levels straight away (a prerequisite, a requirement from another module), and the link lives in the
graph instead of in a message waiting to be delivered.

## The resolver
The resolver answers one question: given a name (and maybe a description), is it the **same as** an existing skill,
**more specific than** one, or **new**? It's used by the API's gates and by the fill job, with the same logic in both.

1. **Find candidates:** an exact match on name or alias, ignoring case, is `same` straight away. Otherwise the eight
   nearest skills by vector similarity are the candidates, and with none at all the name is `new`.
2. **Judge:** a small, fast model looks at the name, its description and the candidates (with their aliases and broader
   skills) and returns `same`, `specialization_of` or `new`, with the candidate it means.
3. **Act:**
   - `same`: use the existing node, and record the new wording as an alias.
   - `specialization_of`: create a stub under that parent.
   - `new`: create a stub with no parent.

A stub is created with its five levels in one transaction. A uniqueness constraint on the name means that if two people
ask for the same new skill at the same moment, the second `MERGE` finds the first one's node instead of creating
another, and only the first publishes `SkillCreated`.

## What the user sees

### Searching
The user lands on the skills module, sees a short explanation of how skills and Dreyfus levels work, and searches. The
search matches names and aliases through a full-text index (each word as a prefix, or with one typo once it's four
letters long) and does a vector search, and combines the two lists by reciprocal rank fusion, so a skill near the top of
either ranks high and one in both ranks higher. It shows the ten closest skills along with their broader parents, so
someone searching "pastry lamination" can see "Baking" too. When the search can't be embedded, it searches by name
alone.

### Opening a skill
- **A `ready` skill** opens straight to its levels. The user can claim a level, attach evidence (uploaded to S3), and
  review the content.
- **A `stub`** shows its name and description and a loading screen while it fills. Opening it is what triggers the fill
  (see below): the UI calls `POST /{id}/fill`, which leaves a skill that is already `filling` or `ready` as it is, so
  it's safe to call on every open. The UI polls `GET /{id}` until it's `ready`.

### Asking for a skill we don't have
If nothing matches, the user can ask for it. The API runs **the gates** before anything is written. The first three are
one structured call to a fast model, and the fourth is the resolver:

1. **Normalize:** fix typos and turn phrasing into a skill name ("being good at excel" becomes "Microsoft Excel").
2. **Classify:** is it actually a skill? "Patience" is a personality facet, "French history" is a topic, "Height" is a
   physical attribute. Those are sent to the right module instead: the API returns the `kind`, and the UI words the
   message and links to that module. Something can be both (Python is a skill and a topic), and that's fine: it's a
   skill here.
3. **Screen:** reject nonsense and slurs. Real skills pass whatever they're about, including violent and sexual ones.
4. **Resolve:** run the resolver on the normalized name. If it says `same`, we show the user "did you mean...?" and, if
   they say yes, add their wording (the normalized name) as an alias, re-embed the skill and publish `SkillAliasAdded`.
   The wording travels in an `alias_token` signed by the API and valid for an hour, so only names that passed the gates
   become aliases. If it says `specialization_of` or `new`, we create the stub.

If the stub is created, the user goes straight into the opening flow above.

## Filling a stub
A stub is filled the first time someone needs it: they open it, try to claim a level of it, or ask for it. Nothing is
filled just because it exists, so the cost of a skill follows how much people actually use it.

1. The API sets the skill to `filling` and publishes `SkillFillRequested`.
2. The fill job picks it up and, in one Bedrock call with a fixed output schema, writes:
   - **Each of the five levels,** with a description, **observable signs** ("can do X without Y"), **example
     evidence** that would show it, and what it takes to reach the next level. Observable signs are what make evidence
     checkable later.
   - **Prerequisites per level,** as names. Each one goes through the resolver. Existing skills are linked to; new ones
     become stubs (and publish `SkillCreated`), but are **not** filled. Before writing a `REQUIRES` link, the job checks
     it wouldn't create a cycle.
3. It sets the skill to `ready`, marks the content `provisional`, and publishes `SkillFilled`.

Requirements on Topics, Physical Attributes, Personality Traits and anything else are written by the modules that own
those sub-graphs. They react to `SkillFilled` and add their own requirements to the levels (see below).

## Community review
Level content is shared by everyone who claims that skill. If one user could rewrite "Competent", every other user's
claim of it would change meaning. So no single user, and no single LLM call, changes the main version on their
own.

### Endorsing
- When a skill is first filled, its content is **version 1, provisional**. It can be claimed right away.
- A user who reads it and thinks it's right **endorses** it. Each endorsement is stored, not just a flag.
- Once enough weighted endorsement builds up, the content becomes **established**.

### Proposing a change
- A user who thinks something is wrong ("this belongs at Proficient, not Expert") writes a **proposal** against a
  level. It's stored as its own node, and doesn't touch the main version.
- The proposal job screens it with an LLM: is it on topic, does it make sense, is it consistent with the other levels?
  Rejected proposals are kept, with the reason, and the user is told why.
- A proposal that passes is opened for endorsement. Other users see it on the skill page and can endorse or oppose it.
- When it gains enough weighted endorsement, and more than it has opposition, it's **promoted**: it becomes the level's
  main content, the level's version goes up by one, the old content is kept as a revision, and `SkillLevelRevised` is
  published.

### How endorsements are weighted
The people best placed to judge a level are the people who have shown they're at or above it. A rough starting point:

| Who endorses | Weight |
|---|---|
| Has a verified claim at or above the level | 3 |
| Has an unverified claim at or above the level | 1 |
| Anyone else | 0.5 |

The weights and the promotion threshold are configuration, not code. With no real users yet they start low, and we
raise them once there's enough traffic to need it.

### Claims remember their version
An `ACHIEVED` relationship records the version of the level it was claimed against. When a level is revised, existing
claims stay attached to the version they were made against, and the person is told the criteria changed so they can
re-confirm.

## Events
Every meaningful change in the skills sub-graph is published as an event, so other modules can react without the Skills
module calling them, or even knowing they exist. This is set up from the start, even while Skills is the only consumer,
because Topics, Physical Attributes, Jobs and others will all need to react to skills appearing and changing.

### The bus
- **One custom EventBridge bus for the whole Atlas** (`atlas-events`). Every module publishes to it, and Skills events
  have the source `atlas.skills`.
- **Each consuming module has its own rule and its own SQS queue,** with a dead-letter queue. One module's backlog or
  failures never hold up another's. The queues can all feed the existing `atlas-jobs` Lambda, which picks a handler by
  the event's `detail-type`, the same way it picks a job type today.
- **The bus has an archive.** When a new module comes along (Topics, say), it can replay every past `SkillFilled` to
  backfill its requirements, instead of us writing a one-off migration.

### The events

| Event | When | Who cares |
|---|---|---|
| `SkillCreated` | A Skill node is created, by any of the three routes | Search indexing, Topics (to link related topics), admin metrics |
| `SkillFillRequested` | Someone needs a stub filled | The Skills fill job |
| `SkillFilled` | A skill's levels are filled for the first time | Topics and Physical Attributes (to add their requirements), Jobs, recommendations |
| `SkillFillFailed` | The fill job gave up | Admin metrics, the UI (through polling) |
| `SkillAliasAdded` | A new name was recorded for a skill | Search indexing |
| `SkillProposalSubmitted` | A user proposed a change | The Skills proposal job |
| `SkillLevelRevised` | A proposal was promoted | Anything that read the old level, such as requirement links and people's claims |
| `SkillLevelClaimed` | A person claimed a level | Profile, recommendations, evidence verification |

The taxonomy import publishes `SkillCreated` too, in batches, so consumers see every skill the same way regardless of
where it came from. Consumers must therefore be cheap to run for a stub.

### What an event looks like
Events are thin. They say what happened and which nodes it happened to, and consumers read the graph for the details.
That keeps events small, and means a consumer always sees the current state rather than a stale copy.

Events name a skill by its `id`, and a level by its skill's `id` and its `rank`.

```json
{
  "source": "atlas.skills",
  "detail-type": "SkillFilled",
  "detail": {
    "eventId": "uuid",
    "schemaVersion": 1,
    "occurredAt": "2026-10-22T14:03:00Z",
    "skillId": "uuid",
    "contentVersion": 1
  }
}
```

### Reliability
- **The graph is the source of truth, and events are published after the write.** If a write succeeds but the publish
  fails, the skill is left in a state such as `filling` with nothing working on it. When the API's `SkillFillRequested`
  publish fails, it puts the skill back to the status it had, so the next person to open it asks again. `SkillCreated`
  and `SkillAliasAdded` failures are logged, since the skill is usable without them.
- **Every consumer is idempotent.** SQS can deliver the same message more than once, so Consumers `MERGE` rather than `CREATE`, and check 
  status before doing work (a fill job that finds the skill already `ready` does nothing).
- **Events carry a `schemaVersion`,** so we can change an event's shape later without breaking older consumers.

## Build order
1. **The event bus,** its archive, and the Skills consumer rule and queue.
2. **The ESCO import,** with embeddings and the uniqueness constraint.
3. **Search and the gates** in the API, with the resolver.
4. **The fill job,** with the resolver for prerequisites, and the cycle check.
5. **Claiming levels,** with evidence and content versions.
6. **Endorsements and proposals,** with the proposal job.
