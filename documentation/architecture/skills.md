# How the Skills Module Works

This explains how the skills sub-graph gets filled out: where skills come from, what a user sees when they search for
one, how new skills get created and fleshed out, how the community keeps them honest, and how the rest of the Atlas
hears about it. For the graph itself, read `../data_model/skills/skills.md`.

## The problem
There are more skills in the world than we could ever write by hand, new ones appear all the time, and people describe
the same skill in many different ways. The skills graph is only useful if each skill exists **once**. If "Knife Skills"
and "Knife Handling" are separate nodes, two people with the same ability never meet in the graph, and everything built
on top of it (who you could become, job matching, recommendations) gets worse.

So the hard part of this module is not generating content, it's **identity**: deciding whether a skill is new, what it
is the same as, and where it sits relative to everything else. The design below is built around that.

## The approach in one paragraph
We start from an existing, curated skills taxonomy (ESCO) so the graph has a backbone on day one. Every skill starts as a cheap **stub**, and only gets its full Dreyfus content generated by an LLM when someone actually needs it. Anything a user types goes through **gates** before it can become a new node. Generated content is **provisional** until the community endorses it, and changes to it are **proposals** that only become the main version once the community accepts them. Every meaningful change is published as an **event**, so other modules (Topics, Physical Attributes, Jobs, and whatever comes next) can react without the Skills module knowing they exist.

## The pieces

| Piece | Where (planned) | What it does |
|---|---|---|
| UI | `application/ui/atlas-of-us-ui/src/skills/` | Search, the skill page, claiming a level, reviewing content and proposals |
| API | `application/apis/atlas-api/src/domains/skills/mod.rs` | Search, the creation gates, claiming levels, endorsements and proposals, publishing events |
| Gates | `application/apis/atlas-api/src/domains/skills/gates.rs` | Normalize and classify what a user asks for, and screen out nonsense |
| Resolver | `application/apis/atlas-shared/src/skills/resolver.rs` | Decides whether a skill name is the same as, more specific than, or different from existing skills, and creates stubs. It's in the crate the API and atlas-jobs share (see `ADRs/atlas_shared_crate.md`), so both run the same logic |
| Fill job | `application/apis/atlas-jobs/src/events/skill_fill_requested/skills.rs` | Generates a stub's Dreyfus levels with Bedrock |
| Prerequisites job | `application/apis/atlas-jobs/src/events/skill_filled/skills.rs` | Links a filled skill's levels to the levels of the skills they need, with the resolver |
| Proposal job | `application/apis/atlas-jobs/src/events/skill_proposal_submitted/skills.rs` | Screens a proposed change before it is opened to the community |
| Event bus | `application/infrastructure/events.tf` | The Atlas event bus, its archive, and one rule and queue per job that reacts to an event |
| Taxonomy import | `application/database/skills_import/` | Asks the API for each ESCO skill, broader skills first |

### Models
- **The gates and the resolver's judge** use a fast model on Bedrock, set by `SMALL_MODEL` in `atlas-shared/src/bedrock.rs` (Claude Haiku
  4.5). Each is one forced tool call whose input is the answer.
- **The fill job** uses the atlas-jobs model, set by `BEDROCK_MODEL_ID` in `jobs_lambda.tf` (Claude Sonnet 4.6), in one
  forced tool call that writes all five levels. **The prerequisites job** uses the same model to name what each level
  needs.
- **Embeddings** come from Amazon Titan Text Embeddings V2 on Bedrock, at 1024 dimensions. A skill's vector is an
  embedding of `"<name>. <description>. Also known as <alias>, <alias>."`, and a search is an embedding of what was
  typed. Why Titan is in `ADRs/skills_embeddings.md`.

### The API
All routes are under `/api/skills`. Asking, confirming and filling need a logged in user.

| Route | What it does |
|---|---|
| `GET /search?q=` | The closest skills, each with the broader skills it's a kind of |
| `POST /` `{query}` | Asks for a skill we don't have: runs the gates and the resolver, and returns an `outcome` of `not_a_skill` (with the `kind` it is), `rejected` (with a `reason`), `existing` (the skill it means) or `created` (the new stub) |
| `GET /{id}` | A skill with its levels, each with the personality traits written on it (`traits`: `name`, `level`, `strength`, `reason`) the levels of other skills it needs (`skills`: the skill's `id`, `name` and `status`, the `rank` of it needed, `strength`, `reason`), and the levels of topics it needs knowledge of (`topics`: the topic's `id`, `name` and `status`, the `rank` of the Bloom level needed, `strength`, `reason`) |
| `GET /{id}/neighbors` | The skill without its levels, and the skills around it: its `broader` skills (the ones it's a kind of), its `narrower` skills (the ones that are kinds of it), what its levels `needs` and what it `leads_to` through `REQUIRES_SKILL` (strongest first, each with the strength of its strongest link), and up to eight `similar` skills by vector, other than its broader and narrower ones. Each comes as a page of twelve with the `total`. It also has every personality trait its levels take, as `traits`, strongest first with the strength of its strongest requirement, and every topic its levels need, as `topics`, strongest first with the strength of its strongest link and the `rank` of the deepest Bloom level any level needs |
| `GET /{id}/neighbors/{group}?skip=` | The next page of `broader`, `narrower`, `needs` or `leads_to`, from `skip` |
| `POST /{id}/fill` | Asks for a `stub` or `failed` skill to be filled, and returns its status |

Every linked skill a route returns comes with its `id`, `name` and `status`.

## Where skills come from
A Skill node is created in exactly three ways, and every one of them goes through the resolver so it can't create a
duplicate:

1. **The taxonomy import.** Our starting backbone. It asks the API for each skill, the same way a user does.
2. **A user searching for something we don't have.** Goes through the gates first.
3. **The prerequisites job naming a prerequisite we don't have.** Goes through the resolver, and is created as a stub,
   never filled until someone needs it.

### The taxonomy: ESCO
ESCO is the European Commission's classification of skills and occupations. It's free to use with attribution, and it
gives us what we would otherwise have to build ourselves:

- **About 14,000 skills,** each with a preferred name, a description and alternative names, in English and many other
  languages.
- **A hierarchy** of broader and narrower skills, which sets the order the import asks for them in.
- **Links between occupations and the skills they need,** which the Jobs module will want later.

How we import it (`application/database/skills_import/`):

- **Only the "skill/competence" entries become Skills.** ESCO also has "knowledge" entries (such as "French history").
  Those belong to the Topics sub-graph, and the topics import asks for them (see "The taxonomy: ESCO" in `topics.md`).
- **Each one is asked for through the API** (`POST /api/skills`), with its ESCO label as what the user typed. The gates
  name it ("use spreadsheets software" becomes "Spreadsheets") and screen it, the resolver decides whether we already
  have it, and the API creates the stub and publishes `SkillCreated`. The import itself only reads the files, so a run
  exercises the API and the events end to end.
- **Broader skills are asked for first,** so the resolver finds them when it places a narrower one.
- **ESCO is only a source.** The graph keeps nothing that ties a skill to ESCO, and an imported skill looks like any
  other.
- **Imports are re-runnable.** The import records the API's answer for every label, and skips labels it has already
  asked for.
- **ESCO is weak on hobbies and everyday skills** (surfing, juggling, sourdough). Those come in through users

## Skill identity

### What a Skill node carries
On top of what `../data_model/skills/skills.md` describes:

- `status`: where it is in its life (see below).
- `aliases`: every other name we know it by.
- `vector`: an embedding of the name, description and aliases, used by the resolver.

### How skills relate to each other
There are three different relationships between skills, and keeping them apart matters:

- **Prerequisite:** lives on the **levels**, not the skills, matching the data model. `(Cooking Competent)-[:REQUIRES_SKILL
  {strength}]->(Knife Skills Advanced Beginner)`. Comes from the prerequisites job. This is the main web between
  skills: what each one needs and what it leads to.
- **Specialization:** `(Sourdough Baking)-[:SPECIALIZATION_OF]->(Baking)`. A kind of another skill, only when everyone
  who has the narrower skill has a form of the broader one. A skill can be a kind of several skills (Data Visualization
  is a kind of Data Analysis and of Graphic Design), and most are a kind of one or none. Comes from the resolver.
- **Same skill:** one node, with the other name in its aliases.

How alike two skills are lives in their vectors, and the vector index works it out when it's needed.

### Statuses

| Status | Meaning |
|---|---|
| `stub` | Exists, can be found and linked to, but its levels are empty |
| `filling` | A fill has been requested and the job is working on it |
| `ready` | Its levels are filled and it can be claimed |
| `failed` | The fill job gave up. The user can retry, which puts it back to `filling` |

Every skill has its five Dreyfus level nodes **from the moment it's created**, even as a stub. That means anything can
link to a stub's levels straight away (a prerequisite, a requirement from another module), and the link lives in the
graph instead of in a message waiting to be delivered.

## The resolver
The resolver answers one question: given a name (and maybe a description), is it the **same as** an existing skill,
and if it's **new**, which existing skills is it a kind of, and which are kinds of it? It's used by the API's gates and by
the prerequisites job, with the same logic in both.

1. **Find candidates:** an exact match on name or alias, ignoring case, is `same` straight away. Otherwise the eight
   nearest skills by vector similarity, scoring at least 0.69 (`MIN_SCORE`), are the candidates, and with none at all
   the name is `new`.
2. **Judge:** a small, fast model looks at the name, its description and the candidates (with their aliases and broader
   skills) and gives a short reason, then the candidate it's the `same` as, if any. Otherwise it lists the candidates
   it's `broader` than, the ones it's a kind of (only the most specific), and the ones that are `narrower`, kinds of it.
   Most names are a kind of one candidate or none.
3. **Act:**
   - `same`: use the existing node.
   - otherwise: create a stub that is a kind of each `broader` skill, with each `narrower` skill a kind of it. When a
     narrower skill already pointed straight at one of the stub's broader skills, that link now runs through the stub,
     so the direct one goes. A `narrower` link that would make a loop is left out.

A stub is created with its five levels and its links in one transaction. A uniqueness constraint on the name means that if two people
ask for the same new skill at the same moment, the second `MERGE` finds the first one's node instead of creating
another, and only the first publishes `SkillCreated`.

## What the user sees

### Searching
The user lands on the skills module, sees a short explanation of how skills and Dreyfus levels work, and searches. The
search matches names and aliases through a full-text index (every word has to match, as a prefix or with one typo once
it's four letters long) and does a vector search that keeps skills scoring at least 0.6, and combines the two lists by reciprocal rank fusion, so a skill near the top of
either ranks high and one in both ranks higher. It shows the ten closest skills along with the broader skills they're a kind
of, so someone searching "pastry lamination" can see "Baking" too. When the search can't be embedded, it searches by name
alone.

### Opening a skill
A skill opens at `/skills/<id>`, with its five levels and, under them, the skills linked to it: the skills it's a kind
of, the kinds of it, what it needs, what it leads to, and similar skills, twelve of each at a time. Each one opens in
turn, and the skills hopped through stay as a trail above the page.

- **A `ready` skill** opens straight to its levels. The user can claim a level, attach evidence (uploaded to S3), and
  review the content. Each level shows the skills it takes, the knowledge it takes and the personality it takes: every
  requirement from that level and the ones below it, strongest first, with how much it matters and why, and the level a carried-up one comes
  from. Each skill it takes names the level of it needed, opens that skill, and is marked when it isn't filled in yet.
  Each topic it needs names the Bloom level of it needed, and opens that topic in Topics.
- **A `stub`** shows its name and description and a loading screen while it fills. Opening it is what triggers the fill
  (see below): the UI calls `POST /{id}/fill`, which leaves a skill that is already `filling` or `ready` as it is, so
  it's safe to call on every open. The UI polls `GET /{id}` until it's `ready`.

### Exploring the graph
The Explorer also has a Graph view: a board in the style of Neo4j Bloom (`GraphBoard` in
`src/shared_components/graph_board.tsx`, which knows nothing about skills, so any sub-graph can use it; see
`ADRs/graph_board.md`). Searching puts a skill on the board.
Double-clicking a skill expands it, bringing every skill linked to it, every personality trait it takes and every
topic it needs onto the board, and a force layout spreads them out. Double-clicking a trait brings on the skills that
take it, strongest first, read with `GET /api/personality/traits/{id}/skills`. Double-clicking a topic brings on the
skills that need it, strongest first, read with `GET /api/topics/{id}/neighbors`, and a topic opens in Topics. Anything on the board can be dragged and stays where it's dropped,
and the board pans and zooms. The board draws five kinds of link, and a legend turns each on and off. Turning a kind
off also hides the skills and traits whose links are all of kinds that are off, other than the selected one, and they
come back where they were when it's turned on again:

- **A kind of:** a solid line with an arrow to the broader skill.
- **Needs:** a dashed line with an arrow to the skill that's needed, thicker for a stronger `REQUIRES_SKILL` link.
- **Similar:** a dotted line.
- **Takes:** a solid red line with an arrow from a skill to a personality trait, thicker for a stronger `REQUIRES_TRAIT`.
- **Knows:** a solid blue line with an arrow from a skill to a topic, thicker for a stronger `REQUIRES_KNOWLEDGE`.

Ready skills are filled in, stubs have a dashed outline, traits are pale blue diamonds, and topics are pale red blobs. Selecting a trait shows
its overview and how many skills take it, and once it's expanded, the next twelve can be brought on. Selecting a skill shows its description and how many of
each kind of link it has, read with `GET /{id}/neighbors`, which never fills it. Expanding brings on the first page of
each kind of link, and a kind with more can bring on the next page. "Open skill" goes to the skill's page, where a stub
gets filled. A skill page has a button that puts its skill on the board, expanded.

### Asking for a skill we don't have
If nothing matches, the user can ask for it. The API runs **the gates** before anything is written. The first three are
one structured call to a fast model, and the fourth is the resolver:

1. **Normalize:** fix typos and turn phrasing into a skill name, a noun phrase for the ability ("being good at excel"
   becomes "Microsoft Excel", "monitor drilling fluid" becomes "Drilling Fluid Monitoring").
2. **Classify:** is it actually a skill? "Patience" is a personality facet, "French history" is a topic, "Height" is a
   physical attribute. Doing something with a subject is a skill ("perform toxicological studies"). Those are sent to the right module instead: the API returns the `kind`, and the UI words the
   message and links to that module. Something can be both (Python is a skill and a topic), and that's fine: it's a
   skill here.
3. **Screen:** reject gibberish, jokes and slurs. Every real skill passes, however narrow, broad or niche, and whatever
   it's about, including violent and sexual ones.
4. **Resolve:** run the resolver on the normalized name. If it says `same`, we show the user the skill they meant. If
   it says the skill is new, we create the stub, linked to the skills it's a kind of and the ones that are kinds of it.

If the stub is created, the user goes straight into the opening flow above.

## Filling a stub
A stub is filled the first time someone needs it: they open it, try to claim a level of it, or ask for it. Nothing is
filled just because it exists, so the cost of a skill follows how much people actually use it.

1. The API sets the skill to `filling` and publishes `SkillFillRequested`.
2. The fill job picks it up and, in one Bedrock call with a fixed output schema, writes **each of the five levels,**
   with a description, **observable signs** ("can do X without Y"), **example evidence** that would show it, and what
   it takes to reach the next level. Observable signs are what make evidence checkable later.
3. It sets the skill to `ready`, marks the content `provisional`, and publishes `SkillFilled`.

### Prerequisites
The prerequisites job (`SkillFilled-Skills`) reacts to `SkillFilled`, for a `ready` skill whose levels have no
prerequisites yet:

1. **Name.** One Bedrock call reads the skill and its five levels and names the other skills each level needs: direct
   prerequisites only, named the way a CV lists a skill, each with a one-sentence description. Each one carries the
   level of this skill it starts at, the level of the other skill needed, a `strength` and a `reason`. It sits on the
   lowest level it applies to, and is named again higher up only when the level needed or the strength changes.
2. **Resolve.** Each name goes through the resolver. A skill we have, under that name, an alias or another phrasing,
   is linked to. A new one becomes a stub, placed under the skills it's a kind of, and publishes `SkillCreated`, but
   is **not** filled. A name that resolves to the skill itself, to a skill it's a kind of, or to a kind of it is
   dropped, since those are specializations.
3. **Write, then check.** Each prerequisite is written as
   `(level)-[:REQUIRES_SKILL {strength, reason}]->(level of the other skill)`. Once that write is committed, the job checks
   whether the other skill now leads back to this one through `REQUIRES_SKILL`, and if it does, takes the link out again.
   Checking after the write means two jobs closing a loop at the same moment can't both miss it: whichever checks
   second sees both links and takes its own out. A loop can exist for the moment between a write and its check.

Requirements on Topics, Physical Attributes, Personality Traits and anything else are written by the modules that own
those sub-graphs. They react to `SkillFilled` and add their own requirements to the levels (see below). The Personality
module links each level to the traits it takes (see "Skill requirements" in `personality.md`), and the Topics module to
the topics it needs knowledge of (see "Skill requirements" in `topics.md`).

## Community review
Level content is shared by everyone who claims that skill. If one user could rewrite "Competent", every other user's
claim of it would change meaning. So no single user, and no single LLM call, changes the main version on their
own.

### Endorsing
- When a skill is first filled, its content is **version 1, provisional**. It can be claimed right away.
- A user who reads it and thinks it's right **endorses** it. Each endorsement is stored, not just a flag.
- Once enough weighted endorsement builds up, the content becomes **established**.

### Proposing a change
- A user who thinks something is wrong ("this belongs at Proficient, not Expert") writes a **proposal** against a
  level. It's stored as its own node, and doesn't touch the main version.
- The proposal job screens it with an LLM: is it on topic, does it make sense, is it consistent with the other levels?
  Rejected proposals are kept, with the reason, and the user is told why.
- A proposal that passes is opened for endorsement. Other users see it on the skill page and can endorse or oppose it.
- When it gains enough weighted endorsement, and more than it has opposition, it's **promoted**: it becomes the level's
  main content, the level's version goes up by one, the old content is kept as a revision, and `SkillLevelRevised` is
  published.

### How endorsements are weighted
The people best placed to judge a level are the people who have shown they're at or above it. A rough starting point:

| Who endorses | Weight |
|---|---|
| Has a verified claim at or above the level | 3 |
| Has an unverified claim at or above the level | 1 |
| Anyone else | 0.5 |

The weights and the promotion threshold are configuration, not code. With no real users yet they start low, and we
raise them once there's enough traffic to need it.

### Claims remember their version
An `ACHIEVED` relationship records the version of the level it was claimed against. When a level is revised, existing
claims stay attached to the version they were made against, and the person is told the criteria changed so they can
re-confirm.

## Events
Every meaningful change in the skills sub-graph is published as an event, so other modules can react without the Skills
module calling them, or even knowing they exist. This is set up from the start, even while Skills is the only consumer,
because Topics, Physical Attributes, Jobs and others will all need to react to skills appearing and changing.

### The bus
- **One custom EventBridge bus for the whole Atlas** (`atlas-events`). Every module publishes to it, and Skills events
  have the source `atlas.skills`.
- **Each job that reacts to an event has its own rule and its own SQS queue,** with a dead-letter queue, named
  `<event>-<module>`: `SkillFillRequested-Skills`, `SkillFilled-Skills`, `SkillFilled-Personality`, `SkillFilled-Topics`. One job's backlog, replay or failures
  never hold up another's, even when several modules react to the same event. Each is one entry in `event_jobs` in
  `events.tf`, with how many of its events run at once. The queues all feed the `atlas-jobs` Lambda, which picks the
  handler by the queue.
- **The bus has an archive.** When a new module comes along (Topics, say), it can replay every past `SkillFilled` to
  backfill its requirements, instead of us writing a one-off migration.

### The events

| Event | When | Who cares |
|---|---|---|
| `SkillCreated` | A Skill node is created, by any of the three routes | Search indexing, Topics (to link related topics), admin metrics |
| `SkillFillRequested` | Someone needs a stub filled | The Skills fill job |
| `SkillFilled` | A skill's levels are filled for the first time | The Skills prerequisites job, Personality, Topics and Physical Attributes (to add their requirements), Jobs, recommendations |
| `SkillFillFailed` | The fill job gave up | Admin metrics, the UI (through polling) |
| `SkillProposalSubmitted` | A user proposed a change | The Skills proposal job |
| `SkillLevelRevised` | A proposal was promoted | Anything that read the old level, such as requirement links and people's claims |
| `SkillLevelClaimed` | A person claimed a level | Profile, recommendations, evidence verification |

The taxonomy import goes through the API, so the API publishes `SkillCreated` for every skill it creates, and consumers
see every skill the same way regardless of where it came from. Consumers must therefore be cheap to run for a stub.

### What an event looks like
Events are thin. They say what happened and which nodes it happened to, and consumers read the graph for the details.
That keeps events small, and means a consumer always sees the current state rather than a stale copy.

Events name a skill by its `id`, and a level by its skill's `id` and its `rank`.

```json
{
  "source": "atlas.skills",
  "detail-type": "SkillFilled",
  "detail": {
    "eventId": "uuid",
    "schemaVersion": 1,
    "occurredAt": "2026-10-22T14:03:00Z",
    "skillId": "uuid",
    "contentVersion": 1
  }
}
```

### Reliability
- **The graph is the source of truth, and events are published after the write.** If a write succeeds but the publish
  fails, the skill is left in a state such as `filling` with nothing working on it. When the API's `SkillFillRequested`
  publish fails, it puts the skill back to the status it had, so the next person to open it asks again. `SkillCreated`
  and `SkillFilled` failures are logged, since the skill is usable without them.
- **Every consumer is idempotent.** SQS can deliver the same message more than once, so Consumers `MERGE` rather than `CREATE`, and check 
  status before doing work (a fill job that finds the skill already `ready` does nothing).
- **Events carry a `schemaVersion`,** so we can change an event's shape later without breaking older consumers.

## Build order
1. **The event bus,** its archive, and the Skills consumer rule and queue.
2. **The ESCO import,** through the API.
3. **Search and the gates** in the API, with the resolver.
4. **The fill job.**
5. **Claiming levels,** with evidence and content versions.
6. **Endorsements and proposals,** with the proposal job.
7. **The prerequisites job,** with the resolver and the cycle check.
